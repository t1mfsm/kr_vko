Подробный разбор проекта kr_vko

1. Общая идея проекта

Проект моделирует работу системы воздушно-космической обороны в Bash под Linux.
Внутри проекта есть несколько независимых процессов:
- генератор целей;
- три РЛС;
- одна система СПРО;
- три ЗРДН;
- командный пункт;
- база SQLite для накопления событий и статистики.

Архитектура построена не на сокетах и не на очередях сообщений, а на файловом обмене:
- генератор пишет отметки целей в каталог `/tmp/GenTargets/Targets`;
- средства поражения пишут запрос на уничтожение в `/tmp/GenTargets/Destroy`;
- все компоненты обмениваются командами с КП через файлы в `messages/`;
- PID-файлы лежат в `pids/`;
- логи пишутся в `logs/`;
- промежуточные результаты проверки выстрела лежат в `temp/shot_results/`.

Смысл модели такой:
- генератор непрерывно создает и двигает цели;
- РЛС обнаруживают цели в своем секторе;
- по двум последним отметкам оценивается скорость и определяется тип цели;
- если баллистическая цель движется к СПРО, РЛС отправляет отдельное предупреждение;
- СПРО стреляет только по баллистическим блокам;
- ЗРДН стреляют только по самолетам и крылатым ракетам;
- командный пункт собирает все сообщения, журналирует события, ведет БД и контролирует живучесть систем через heartbeat.

2. Разбор файлов в корне проекта

2.1. `README.md`

Это пользовательское описание проекта.
Что в нем есть:
- назначение проекта;
- состав системы и координаты варианта;
- список файлов;
- зависимости: `sqlite3`, `bc`, `openssl`, `xxd`;
- команды запуска и остановки;
- примеры просмотра логов;
- описание базы данных и готовых SQL-запросов;
- краткое словесное описание логики системы.

Файл нужен как входная точка для преподавателя или пользователя: по нему можно быстро понять, что именно моделируется и как запускать проект.

2.2. `config.sh`

Это центральный файл конфигурации. Почти все остальные скрипты его используют напрямую или через `common.sh`.

Что именно он задает:
- абсолютные базовые каталоги проекта: `db`, `logs`, `messages`, `temp`, `pids`;
- рабочие каталоги генератора целей: `TARGETS_DIR` и `DESTROY_DIR`;
- HMAC-ключ для подписи сообщений между компонентами;
- временные интервалы:
  - `CHECK_INTERVAL`;
  - `TARGET_STALE_SECONDS`;
  - задержки проверки результата выстрела;
  - параметры heartbeat;
  - время автопополнения боекомплекта;
- лимит строк для ротации логов;
- параметры всех объектов варианта:
  - три РЛС;
  - три ЗРДН;
  - одна СПРО;
- диапазоны скоростей для классификации целей:
  - `BB_BR` для баллистических блоков;
  - `KR` для крылатых ракет;
  - `SAM` для самолетов.

По сути это "паспорт" сценария. Если изменить этот файл, можно поменять географию, радиусы, боекомплект и критерии распознавания, не трогая остальной код.

2.3. `common.sh`

Это главный библиотечный файл проекта. Он содержит почти всю общую инфраструктуру, на которой работают остальные процессы.

Ключевые функции:

`check_environment()`
- запрещает запуск от `root`;
- требует Linux;
- требует Bash версии не ниже 4.

`check_single_instance(name)`
- не дает запустить второй экземпляр того же компонента;
- использует PID-файл в каталоге `pids/`.

`cleanup(name)`
- удаляет PID-файл при завершении процесса.

`decode_target_id(filename)`
- восстанавливает ID цели из имени файла в каталоге генератора;
- это важно, потому что генератор не хранит ID открыто в имени, а вплетает его в псевдослучайную hex-строку;
- таким образом все средства обнаружения читают имя файла, достают из него ID и дальше работают с ним как с постоянным идентификатором цели.

`calc_distance()`
- считает расстояние между двумя точками через `bc` и `sqrt`.

`calc_speed()`
- в текущей реализации фактически равен расстоянию между двумя отметками;
- используется для оценки перемещения за один интервал.

`calc_speed_mps()`
- более точная версия, учитывающая интервал времени в миллисекундах;
- в основном коде почти не задействована, но подготовлена как вспомогательная функция.

`get_target_type(speed)`
- классифицирует цель по скорости:
  - от 8000 м/с и выше: `BB_BR`;
  - от 250 до 999 м/с: `KR`;
  - от 50 до 249 м/с: `SAM`;
  - иначе `UNKNOWN`.

`is_in_range()`
- проверяет попадание цели в круговую зону.

`is_in_sector()`
- проверяет попадание цели в сектор РЛС;
- сначала проверяет дальность;
- затем считает угол до цели;
- для вычисления угла использует `awk` и `atan2`;
- отдельно учитывает сектор, который может пересекать 0 градусов.

`is_moving_toward_spro()`
- проверяет, движется ли цель в сторону СПРО;
- делает это через скалярное произведение:
  - берется вектор движения цели;
  - берется вектор от текущего положения цели к СПРО;
  - если скалярное произведение положительное, цель движется в сторону СПРО.

`log_message(logfile, system_name, message)`
- добавляет строку с меткой времени в лог;
- выполняет простую ротацию логов, если строк стало больше `MAX_LOG_LINES`.

`encrypt_message()` и `decrypt_message()`
- это не полноценное шифрование, а упаковка сообщения:
  - полезная нагрузка кодируется в base64;
  - сверху считается HMAC-SHA256 на общем ключе;
  - формат хранения: `base64|hmac`.
- при приеме сообщения проверяется целостность;
- если подпись не совпала, возвращается `ERROR_HMAC`;
- если base64 не декодируется, возвращается `ERROR_DECRYPT`.

`send_to_kp()` и `send_from_kp()`
- отправляют сообщения через файловые очереди:
  - в `messages/to_kp`;
  - в `messages/from_kp`.

`send_heartbeat_response()`
- создает heartbeat-ответ в специальной директории.

`read_target_coords(filepath)`
- читает первую строку файла цели;
- извлекает координаты `X` и `Y`.

`get_latest_target_file()`, `get_latest_target_mtime()`, `get_latest_fresh_target_mtime()`
- помогают находить самую свежую отметку конкретной цели.

`track_shot_result_async()`
- одна из ключевых функций проекта;
- запускает фоновую проверку результата выстрела;
- идея такая:
  - после выстрела система ждет фиксированную задержку;
  - затем смотрит, появились ли новые отметки цели;
  - если свежие отметки продолжают идти, считается, что был промах;
  - если новых отметок нет, считается, что цель уничтожена;
  - результат пишется в лог, отправляется на КП и сохраняется во временный файл.

`get_file_mtime()`
- получает время модификации файла в миллисекундах;
- старается быть совместимым с разными реализациями `find/stat`.

`scan_targets()`
- очень важная функция;
- просматривает каталог `TARGETS_DIR`;
- для каждой цели выбирает только самый свежий файл;
- отбрасывает слишком старые отметки;
- возвращает список активных целей в формате:
  `ID X Y MTIME`.

`get_latest_two_visible_marks()`
- находит две последние отметки конкретной цели;
- проверяет, что последняя отметка уже находится в зоне конкретной системы;
- нужна для классификации цели по скорости на второй засечке.

`db_insert()` и `init_database()`
- работают с SQLite;
- создают и используют таблицы:
  - `journal` для общего журнала;
  - `system_status` для статусов и остатка БК;
  - `shots` для результатов стрельбы;
  - `nsd_log` для попыток несанкционированного воздействия.

Итог: `common.sh` фактически является каркасом всей системы. Без него остальные скрипты были бы сильно дублированы.

2.4. `GenTargets.sh`

Это генератор целей. Он работает как отдельный бесконечный процесс и моделирует воздушно-космическую обстановку.

Главные идеи скрипта:
- держит массив целей в памяти;
- умеет создавать новую цель и обновлять уже существующую;
- хранит для каждой цели:
  - ID;
  - тип;
  - координаты;
  - скорость по X;
  - скорость по Y;
  - полную скорость;
  - время жизни `ttl`.

Как он создает новую цель:
- случайно выбирает тип:
  - `b` баллистическая;
  - `s` самолет;
  - `r` ракета;
- по таблицам выбирает диапазон скоростей и время жизни;
- случайно раскладывает скорость на составляющие `SpeedX` и `SpeedY`;
- случайно выбирает направления движения;
- подбирает стартовые координаты так, чтобы цель не рождалась прямо у края карты;
- создает ID из случайной hex-строки плюс суффикс типа.

Как он обновляет цель:
- изменяет координаты на вектор скорости;
- уменьшает `ttl`;
- создает новый файл отметки в `/tmp/GenTargets/Targets`;
- в имени файла прячет ID цели, чтобы потом его можно было декодировать;
- в содержимом файла пишет координаты `X` и `Y`.

Как обрабатывается поражение:
- средства поражения создают файл с именем цели в `/tmp/GenTargets/Destroy`;
- генератор замечает этот файл;
- с вероятностью `Probability=70` цель считается уничтоженной;
- иначе считается, что был промах;
- если цель уничтожена, запись в массиве очищается и генерация для этого слота начнется заново.

Дополнительные особенности:
- есть режим текстовой карты при запуске с `map` или `-map`;
- периодически удаляются старые файлы отметок;
- собственный лог ведется в `/tmp/GenTargets/GenTargets.log`, а не в `logs/`.

По роли в системе это источник "истины" о целях. Все РЛС, СПРО и ЗРДН видят только следствия его работы.

2.5. `rls.sh`

Это единый скрипт для трех РЛС. Номер станции передается первым аргументом: `1`, `2` или `3`.

Что делает скрипт:
- выбирает из `config.sh` параметры конкретной РЛС через `eval`;
- создает PID-файл;
- заводит собственный лог;
- сообщает КП о статусе `ONLINE`.

Основной цикл:

1. Обработка heartbeat
- если КП положил файл-запрос heartbeat, РЛС удаляет его и создает ответ.

2. Обработка входящих команд от КП
- читает файлы из `messages/from_kp`, адресованные этой РЛС;
- проверяет HMAC;
- если подпись неверна, логирует попытку подмены и сообщает об этом на КП.

3. Сканирование пространства
- вызывает `scan_targets()` и получает список активных целей;
- оставляет только те, что попадают в сектор данной РЛС.

4. Обнаружение новой цели
- если цель еще не докладывалась, РЛС пытается получить две последние отметки;
- по двум последним координатам считает скорость;
- по скорости определяет тип цели;
- пишет лог и отправляет на КП сообщение вида:
  `DETECT target_id x y type speed`.

5. Дополнительный анализ для баллистических целей
- если цель классифицирована как `BB_BR`;
- проверяется, движется ли она в сторону СПРО;
- если да, и предупреждение еще не отправлялось, РЛС отправляет `SPRO_ALERT`.

6. Очистка памяти
- если цель пропала из сектора, она удаляется из внутренних ассоциативных массивов;
- при повторном входе в сектор она может быть обнаружена заново.

Важный момент:
- РЛС не стреляет;
- ее задача только обнаружить, классифицировать и доложить.

2.6. `spro.sh`

Это скрипт системы противоракетной обороны.

Что он знает о себе:
- координаты СПРО;
- радиус действия;
- начальный боекомплект;
- имя лог-файла.

На старте:
- сообщает о включении;
- отправляет на КП сообщение `STATUS ... ONLINE AMMO:n`.

Главный цикл:

1. Heartbeat
- отвечает на запросы КП.

2. Сообщения от КП
- читает команды из `messages/from_kp`;
- проверяет HMAC;
- умеет реагировать на `REFILL`, то есть пополнение боекомплекта.

3. Автопополнение БК
- если боекомплект обнулен, запускается таймер;
- через `AMMO_REFILL_TIME` секунд боекомплект восстанавливается автоматически.

4. Сканирование целей
- через `scan_targets()` получает все текущие цели;
- оставляет только те, что в круговой зоне СПРО.

5. Обнаружение и классификация
- как и РЛС, по двум последним отметкам вычисляет скорость и тип;
- отправляет на КП `DETECT`.

6. Стрельба
- СПРО стреляет только по `BB_BR`;
- если боекомплект больше нуля:
  - создает файл в `DESTROY_DIR` с ID цели;
  - уменьшает боекомплект;
  - ставит цель на внутренний контроль как обстрелянную;
  - запускает `track_shot_result_async()`.

7. Результат выстрела
- фоновая функция позднее определяет `DESTROYED` или `MISS`;
- когда во временном каталоге появляется результат, СПРО снимает блокировку с цели и может снова работать дальше.

Особенность логики:
- СПРО совмещает функции обнаружения и поражения;
- в реальной архитектуре такое решение упрощает модель: СПРО не ждет внешнего целеуказания, а сама видит цель в своей зоне.

2.7. `zrdn.sh`

Это скрипт зенитного ракетного дивизиона. Один и тот же файл обслуживает три ЗРДН.

Структурно он очень похож на `spro.sh`, но с двумя важными отличиями:
- использует параметры выбранного ЗРДН;
- стреляет только по `SAM` и `KR`, но не по `BB_BR`.

Логика работы:
- отвечает на heartbeat;
- принимает от КП команды, в том числе `REFILL`;
- автоматически пополняет боекомплект после паузы;
- сканирует цели в круговой зоне;
- определяет тип по скорости на второй отметке;
- отправляет `DETECT` на КП;
- если цель самолет или крылатая ракета и есть БК, делает выстрел;
- дальше через `track_shot_result_async()` получает `MISS` или `DESTROYED`.

Почему ЗРДН и СПРО разделены:
- это отражает разделение по типам угроз;
- баллистические цели отданы СПРО;
- аэродинамические цели отданы ЗРДН.

2.8. `kp.sh`

Это центральный управляющий и журналирующий узел проекта. Самый важный скрипт после `common.sh`.

Основные задачи КП:
- принимать сообщения от всех средств;
- проверять их целостность;
- фиксировать события в логах;
- писать события в БД;
- следить за доступностью систем через heartbeat.

Что происходит на старте:
- инициализируется БД;
- создаются ссылки на общий лог КП и системный журнал;
- формируется список всех контролируемых систем;
- для каждой системы подготавливаются структуры статуса и счетчиков пропусков heartbeat.

Основной цикл КП состоит из двух больших частей.

Первая часть: обработка всех входящих сообщений из `messages/to_kp`

Типы сообщений и реакция:

`STATUS`
- обновляет статус системы;
- пишет его в лог;
- заносит запись в `system_status` и `journal`.

`DETECT`
- фиксирует факт обнаружения цели;
- сохраняет координаты, тип и систему-источник;
- пишет в `journal`.

`SPRO_ALERT`
- фиксирует предупреждение РЛС о движении баллистической цели к СПРО.

`SHOT`
- фиксирует выстрел;
- записывает событие в `journal`;
- при наличии значения `AMMO:n` дополнительно сохраняет остаток БК в `system_status`.

`DESTROYED`
- фиксирует успешное поражение;
- записывает результат в `shots` и `journal`.

`MISS`
- фиксирует промах;
- тоже пишет в `shots` и `journal`.

`AMMO_EMPTY`
- отмечает исчерпание боекомплекта;
- записывает это в журнал и статусную таблицу.

`REFILL`
- отмечает пополнение боекомплекта;
- обновляет `system_status`.

`NSD`
- фиксирует попытки несанкционированного воздействия;
- пишет в `nsd_log` и `journal`.

Если HMAC у входящего сообщения не проходит проверку:
- событие считается подменой или порчей;
- это отдельно логируется;
- информация записывается в `nsd_log`.

Вторая часть: heartbeat-мониторинг

Как это работает:
- раз в `HEARTBEAT_INTERVAL` секунд КП создает heartbeat-запрос для каждой системы;
- затем ждет `HEARTBEAT_RESPONSE_TIMEOUT` секунд;
- если ответ получен и проверка HMAC проходит:
  - счетчик пропусков обнуляется;
  - система отмечается как `ONLINE`;
  - если до этого была `OFFLINE`, фиксируется восстановление работоспособности;
- если ответ не получен:
  - увеличивается счетчик пропусков;
  - после `HEARTBEAT_MISSES_BEFORE_OFFLINE` подряд пропусков система считается `OFFLINE`;
  - это пишется в лог и БД.

Почему `kp.sh` важен:
- без него проект распадется на отдельные процессы;
- именно КП собирает из локальных событий цельную картину работы всей системы.

2.9. `start.sh`

Это скрипт запуска проекта.

Что он делает:
- проверяет, что запуск идет не от root, в Bash и под Linux;
- создает нужные каталоги проекта;
- создает каталоги генератора в `/tmp`;
- подключает `common.sh` и инициализирует БД.

Функция `start_component()` умеет запускать:
- генератор;
- КП;
- РЛС1-3;
- СПРО;
- ЗРДН1-3.

Если `start.sh` вызван без аргумента:
- удаляет старую БД;
- очищает очереди сообщений;
- заново создает БД;
- запускает систему в правильном порядке:
  - сначала генератор;
  - затем КП;
  - потом РЛС;
  - затем СПРО;
  - затем ЗРДН.

Этот порядок неслучаен:
- сначала должен появиться источник целей;
- затем центр сбора сообщений;
- затем средства обнаружения и поражения.

Если передан аргумент, можно запускать отдельный компонент, например `./start.sh rls2`.

2.10. `stop.sh`

Это скрипт остановки проекта.

Что он делает:
- читает PID-файлы;
- пытается завершить процесс обычным `kill`;
- если процесс не остановился, применяет `kill -9`;
- очищает PID-файл.

Функция `stop_by_name()` умеет останавливать конкретный компонент по короткому имени.

Если скрипт вызван без аргументов:
- останавливает систему в обратном порядке:
  - сначала ЗРДН;
  - потом СПРО;
  - затем РЛС;
  - затем КП;
  - затем генератор;
- дополнительно чистит файловые очереди сообщений.

Это штатный инструмент корректного завершения работы модели.

2.11. `db_queries.sh`

Это не часть боевой логики, а готовый аналитический инструмент.

Скрипт подключает `config.sh`, находит БД и выводит набор SQL-отчетов:
- остаток боеприпасов по СПРО и ЗРДН;
- количество уничтоженных целей по системам;
- самая результативная система;
- точность стрельбы по проценту попаданий;
- последние обнаруженные цели;
- список целей, летевших в сторону СПРО;
- последние промахи;
- попытки НСД;
- суммарную статистику;
- количество целей, уничтоженных ЗРДН за последний час.

Почему этот файл полезен:
- демонстрирует, что БД в проекте не декоративная;
- данные действительно используются для анализа работы системы.

2.12. `map.png`

Это графическая карта варианта.
Код ее не обрабатывает напрямую, но она нужна как визуальная опора:
- для понимания расположения РЛС;
- для понимания зон ответственности;
- для соотнесения координат объектов из `config.sh`.

5. Разбор каталогов служебного обмена

5.1. `messages/`

Это файловая шина обмена сообщениями.

`messages/to_kp`
- сюда системы кладут сообщения для КП.

`messages/from_kp`
- сюда КП кладет сообщения для конкретных систем.

`messages/heartbeat`
- здесь живут heartbeat-запросы и ответы.

В текущем состоянии каталоги пустые, что нормально, если система сейчас не запущена.

5.2. `pids/`

Здесь лежат PID-файлы процессов.
Они нужны:
- для запрета двойного запуска;
- для корректной остановки через `stop.sh`.

5.3. `temp/`

Временный каталог проекта.

`temp/shot_results`
- сюда `track_shot_result_async()` пишет результат проверки выстрела;
- основной процесс СПРО или ЗРДН читает этот файл и снимает блокировку с цели.

6. Как работает проект по шагам

1. `start.sh` создает окружение и запускает все процессы.
2. `GenTargets.sh` генерирует цели и начинает писать их отметки в `/tmp/GenTargets/Targets`.
3. РЛС, СПРО и ЗРДН периодически вызывают `scan_targets()` и отбирают цели, попавшие в их зоны.
4. Для новой цели система берет две последние отметки.
5. По разнице координат вычисляется скорость.
6. По скорости определяется тип цели.
7. РЛС отправляют только информацию на КП.
8. СПРО и ЗРДН не только обнаруживают, но и пытаются уничтожать цели.
9. Для выстрела создается файл в `Destroy`, который читает генератор.
10. Генератор случайным образом решает, было ли поражение.
11. Через несколько секунд фоновой проверкой определяется `MISS` или `DESTROYED`.
12. КП принимает все сообщения, ведет логи и БД.
13. Параллельно КП следит, отвечает ли каждая система на heartbeat.

7. Что особенно важно в коде

1. Проект асинхронный.
Каждый компонент работает в своем бесконечном цикле и общается через файловую систему.

2. Источник данных только один.
Истинное положение целей определяет только генератор `GenTargets.sh`.

3. Классификация цели построена на скорости.
Тип цели не хранится явно в отметке; система выводит его по величине перемещения между двумя последними отметками.

4. Есть элемент имитации боевой неопределенности.
Даже после выстрела результат не гарантирован: генератор применяет вероятность поражения 70%.

5. Есть контроль целостности сообщений.
Хотя связь реализована через файлы, проект не просто копирует текст, а подписывает его HMAC.

6. КП реализует централизованное наблюдение.
Он не отдает сложных команд наведения, но собирает всю телеметрию и ведет контроль состояния.

8. Ограничения и особенности реализации

1. Это учебная модель, а не физически точный расчет.
Скорость определяется по смещению отметок, без полноценной кинематики и без высоты.

2. Файловый обмен прост, но не идеален.
Возможны гонки по времени появления и удаления файлов, хотя для учебной задачи это приемлемо.

3. В коде есть зависимость от Linux-инструментов.
Проект рассчитан именно на Bash под Linux.

4. `sqlite3` нужен для аналитики и БД.
В текущей Windows-среде при разборе он не был установлен, поэтому схему БД пришлось читать через Python.

5. В исходниках и логах видны проблемы отображения кириллицы в текущей консоли Windows.
Сами файлы содержат русский текст, но при чтении в текущей кодировке часть строк отображалась как "кракозябры".
Это проблема окружения просмотра, а не логики скриптов.
